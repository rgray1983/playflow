# Sprint 011 — Parent booking through unpaid hold

The Parent Portal now has a Book a party dialog. A verified, linked parent chooses an existing active child, event type, package, optional add-ons, date and available time. Contact details come from the saved parent profile. Review includes the current server quote, fees/tax, deposit, venue timezone and setup access. Missing child liability coverage can be signed in the wizard using the existing per-child signing endpoint. The rental agreement is the final step; its signature atomically saves the reservation and immutable booking/price snapshot.

The server reuses the staff booking availability/pricing rules, checks family/child ownership and valid liability evidence, locks venue reservations, and rejects a changed quote or unavailable slot before saving. Identical retries return the same reservation; changed retries fail. The hosting child is added with the exact liability coverage reference. Agreement, booking, add-ons, guest and timeline persist in one transaction.

Reservations stay PENDING / AWAITING_DEPOSIT, unpaid and unconfirmed, with a 48-hour hold. No card fields, payment API calls, synthetic payment receipts, confirmation tokens or invitation tokens are created by this flow. The final screen and portal list explain that checkout is unavailable and parents should contact the venue to arrange a deposit. Up to two unexpired pending holds per parent are allowed. Parents may cancel their own unpaid pending hold with an explicit confirmation disclosure; paid or confirmed bookings require staff. Cancellation and staff payment operations share the tenant reservation lock.

No new schema or database branch is needed. No Wix records are imported or changed. No live legal agreement is signed by automated tests. Square sandbox/live checkout, webhooks and payment-gated confirmation, guest invitation release, automated communications, rescheduling and final brand/mobile visual review remain future work. Staff can still manually collect and confirm through existing staff actions.

Validation: parent guards and cross-site rejection, saved account authority, trusted pricing, child/waiver evidence, required agreement acknowledgments, stale quotes/catalog, retry deduplication and conflicting reservations, transaction rollback, hold limits/expiration, and cancellation ownership/payment restrictions. Existing payment, calendar, RSVP, auth and waiver suites run alongside these tests.

## Follow-up — confirmed party links

Both staff confirmation and existing confirmation-link handling now create separate host/guest credentials if missing. Confirmed bookings display a private Party host dashboard and a shareable Guest invitation/RSVP link (with Copy button) in the authenticated hosting parent's portal. Pending/cancelled bookings do not expose these portal links. Existing confirmed bookings repair missing links through scoped POST handlers when opened in the portal or staff event manager; the tenant lock serializes creation and existing credentials are preserved. Guest invitations never contain host credentials. No email is sent by link generation.
